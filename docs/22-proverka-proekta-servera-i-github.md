## Подключение и фактическая проверка сервера

### Причина и проверка

На компьютере включён SotaVPN, интерфейс `tun0` (`sing-tun Tunnel`). `Find-NetRoute` показал, что обращения к `159.194.245.43` идут через него, по маршруту `128.0.0.0/3` с next hop `172.19.0.2`.

SSH находил и читал ключ `C:/Users/LionPro/.ssh/mama_vps`, устанавливал TCP-соединение, но не получал SSH banner. HTTPS по IP с правильным именем TLS также завершался таймаутом. Это происходило до авторизации: новые ключи и пароли не требовались.

С временным маршрутом только к VPS напрямую через Wi-Fi SSH успешно авторизовался, HTTPS вернул `200` и `{"ok":true,"failed":[]}`. Временный маршрут затем удалён. Таким образом, проверка подтвердила проблему пути через VPN; внутренняя причина сбоя Sota не устанавливалась.

### Сохранённое решение

После успешного теста через UAC сохранён постоянный маршрут стандартной утилитой Windows:

```powershell
route.exe -p ADD 159.194.245.43 MASK 255.255.255.255 192.168.0.1 METRIC 1 IF 27
```

Параметры на этом компьютере:

- цель — только `159.194.245.43/32`;
- интерфейс 27 — «Беспроводная сеть 7», TP-Link Wireless USB Adapter;
- шлюз — `192.168.0.1`;
- IP компьютера на момент настройки — `192.168.0.121`.

Остальные адреса этим маршрутом не затрагиваются, SotaVPN не отключался. Постоянный маршрут предназначен для сохранения после перезагрузки; сама перезагрузка не выполнялась. При смене сети, шлюза, адаптера или IP VPS маршрут потребуется пересмотреть.

Первая попытка сохранить маршрут через `New-NetRoute -PolicyStore PersistentStore` вернула ошибку параметра. Успешное сохранение и проверка выполнены через `route.exe -p ADD`.

Удаление этого исключения при необходимости (PowerShell от администратора; в этом шаге не выполнялось):

```powershell
route.exe DELETE 159.194.245.43 MASK 255.255.255.255 192.168.0.1 IF 27
```

## Проблемы и ограничения проверки восстановления

1. **Образ без pgvector.** `infra/backup/restore-check.sh` поднимает временный `postgres:16-alpine`, тогда как текущая схема содержит расширение `vector` и таблицу с `vector(384)` (миграция `0007`). В скрипте нет установки расширения. Для дампа с новой схемой ожидается ошибка восстановления. Это вывод по коду, а не результат запуска скрипта.
2. **Медиа не проверяются восстановлением.** Скрипт разворачивает SQL и считает таблицы, материалы и пользователей, но не восстанавливает архив медиа и не проверяет файлы в S3. Даже успешный SQL-прогон не докажет полное восстановление проекта.
3. **Проверка считает объекты, но не сравнивает их с эталоном.** Количество таблиц и записей выводится, однако ожидаемые значения не задаются. Нужны заранее определённые критерии успешности.
4. **Uptime Kuma размещён на том же VPS.** В текущем Compose мониторинг работает на общем сервере с приложением. При полном отключении VPS сам этот экземпляр Kuma не сможет отправить уведомление. Формулировку в эксплуатационной инструкции о контроле полного падения сервера нужно уточнить; наличие отдельного внешнего монитора неизвестно.

Скрипты не запускались и не исправлялись. Проверку восстановления следует выполнять изолированно, на совместимом с текущим дампом образе и без изменения рабочей БД.
